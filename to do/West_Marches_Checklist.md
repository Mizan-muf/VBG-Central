# West Marches Module Checklist

## Design pillars

- [ ] Characters begin and end active quests at the Hub.
- [ ] Quests are small, self-contained expeditions that resolve within one 24-hour real-world window.
- [ ] A completed quest always produces a clear result: success, partial success, failure, or withdrawal.
- [ ] Quest outcomes permanently reshape the shared world: routes, threats, factions, locations, resources, or future quests.
- [ ] GMs author and approve quests; participating players run the scene using its stated procedures.
- [ ] Hub activities and events give players meaningful play between expeditions.

## Core rules to lock first

- [ ] Choose the module's resolution engine and health/recovery overrides after base VBG decisions are finalized.
- [ ] Define the in-world time represented by a 24-hour quest window.
- [ ] Define the maximum party size, minimum party size, and whether a quest may start solo.
- [ ] Define how absent, late, or withdrawn players are handled without blocking resolution.
- [ ] Define death, injury, rescue, and return-to-Hub procedures.
- [ ] Define the GM's final authority when self-run play needs an interpretation.

## Quest board and expedition loop

- [ ] Create a standard Quest Brief template: title, hook, objective, region, recommended party size, expected risks, deadline, rewards, and world-state stakes.
- [ ] Give each quest a unique ID, status, owner/GM, and a visible 24-hour start and end time.
- [ ] Define how players claim a quest, form a party, and declare departure from the Hub.
- [ ] Require the brief to state the information players need to run it: scenes, threats, target numbers or difficulty bands, clocks, likely consequences, and success/failure branches.
- [ ] Define what player-run resolution may decide and what requires a GM ruling.
- [ ] Support conditional actions and a clear response deadline inside the 24-hour quest window.
- [ ] Define automatic closure at the deadline: resolve the current scene, apply a stated fallback, and return surviving characters to the Hub when possible.
- [ ] Create a Quest Report template for players: result, rolls, loot spent/gained, injuries, discoveries, and proposed world changes.
- [ ] Require a GM to verify the report, award progression, and update the world ledger.

## World progression

- [ ] Create a shared regional map with locked, known, explored, and changed locations.
- [ ] Track each quest's permanent consequences in a world ledger.
- [ ] Define consequence categories: route opened/closed, threat raised/lowered, faction standing, resource availability, landmark change, and new quest hook.
- [ ] Create faction clocks or reputation tracks with visible thresholds and effects.
- [ ] Create regional threat clocks that can unlock escalations, crises, or rare opportunities.
- [ ] Define when completed quests retire, repeat, evolve, or create follow-up quests.
- [ ] Establish rules for unique discoveries, scarce resources, and contested rewards.

## Rewards and advancement

- [ ] Set quest reward bands for success, partial success, failure, and withdrawal.
- [ ] Separate personal rewards (PP, gear, traits) from communal rewards (Hub upgrades, map progress, faction access).
- [ ] Define reward splitting, shared loot, claimed loot, and inventory limits.
- [ ] Define repeatable-quest rewards and anti-farming limits.
- [ ] Define advancement timing and whether it can occur only at the Hub.

## Hub play

- [ ] Define Hub locations and services: quest board, traders, crafting, healing, training, social spaces, storage, and faction representatives.
- [ ] Define downtime actions, costs, limits, and duration.
- [ ] Add player projects: build facilities, research discoveries, establish trade, recruit allies, or improve defenses.
- [ ] Define Hub upgrades and their shared mechanical benefits.
- [ ] Create rumor, notice-board, and player-led scene procedures.

## Activities and events

- [ ] Create a lightweight format for non-quest Hub activities: contests, festivals, duels, games, markets, performances, and social scenes.
- [ ] Define event reward limits so activities remain fun without outclassing expeditions.
- [ ] Create a limited-time event template with start/end time, participation rules, unique stakes, and resolution procedure.
- [ ] Create repeatable activities with reset timing and capped rewards.
- [ ] Create world events that populate the Hub and feed quest hooks: visiting caravans, faction meetings, emergencies, celebrations, and seasonal changes.
- [ ] Define whether events can alter faction, Hub, or regional clocks.

## GM operations

- [ ] Build a quest-design checklist that prevents oversized quests and guarantees a 24-hour resolution path.
- [ ] Build encounter and difficulty guidance by party size and character progression.
- [ ] Define how GMs publish, reserve, revise, cancel, and archive quests.
- [ ] Define moderation, dispute-resolution, spoiler, and safety procedures for the server.
- [ ] Create a canonical tracker for quests, characters, regions, factions, clocks, Hub upgrades, and events.
- [ ] Run a small playtest: three self-run quests, one deadline closure, one Hub event, and one world-state update.
